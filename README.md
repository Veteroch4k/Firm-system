## 🎯 О проекте
Firm System — это RESTful API, разработанное на базе Spring Boot. Приложение представляет собой фрагмент информационной системы производственной фирмы, который будет обеспечивать
*  Управление производственным циклом инструментов
*  Управление производственным циклом материалов
*  Управление выпускаемой продукцией
*  Управление операциями
*  Управление нарядами
*  Управление цехами
*  Ведение отчетности

### 🔨 Сборка проекта

1. **Клонируйте репозиторий:**
   ```bash
   git clone https://github.com/Veteroch4k/Firm-system.git
   cd Firm-system
   ```

2. **Соберите все модули:**
   ```bash
   ./gradlew build
   ```
### 🚀 Запуск приложения

Выберите один из следующих вариантов развертывания:

#### Вариант 1: Поднятие всех сервисов
Идеально для локального запуска и тестирования функциональности:  
(*Не забудьте перейти в директорию c **docker-compose.yaml** файлом: /docker*)
```bash
# Первый запуск
docker-compose up -d

# Повторный запуск
docker-compose start

# Запуск отдельного контейнера
docker-compose start <название сервиса>
```
#### Вариант 2: Локальное тестирование
Если хочется проверить работу пары отдельных сервисов 
```bash
# Первый запуск
docker-compose up -d postgres config-server <название сервиса>

# Повторный запуск 
docker-compose start

# Запуск отдельного контейнера
docker-compose start <название сервиса>
```
### 🛑 Остановка сервисов

```bash
# Остановка и удаление всех контейнеров
docker-compose down

# Остановка всех контейнеров (без удаления)
docker-compose stop

# Точечная остановка
docker-compose stop <название_контейнера>
```

## 🔐 Keycloak Security Конфигурация
В директории docker/ лежит файл конфигурации для Keycloak, который импортируется при первом запуске. Создаются два пользователя с ролью 'USER' user-user и 'ADMIN' veteroch4k-admin (login-password) в firm-realm и глобальный admin-admin.
Однако же, если вдруг конфигурация не применилась - ниже описаны шаги по настройке Keycloak

### 1. Создайте реалм firm-realm
1. Откройте интерфейс Keycloak (`http://localhost:8181`).
2. В левом меню нажмите на выпадающий список (там будет либо Keycloak, либо master)
3. Нажмите **Create realm** 
4. В поле **Realm name** впишите firm-realm и переключите **Enabled** на 'on'.

### 2. Создайте роль ADMIN
1. Перейдите в только что созданный нами реалм (в том же выпадающем меню, где мы создали его)
2. Перейдите в раздел **Realm Roles** и нажмите **Create Role**
3. Назначьте имя 'ADMIN', описание можно оставить пустым
4. Нажмите **Save**
5. Name the role **`ADMIN`** and click **Save**.

### 3. Создайте ADMIN-юзера 
1. Перейдите в раздел **Users** и нажмите **Add user**
2. **Email verified** переключите на 'Yes'
3. Заполните username (в моем случае veteroch4k)
4. Нажмите **Save** и перейдите в **Credentials**.
5. Назначьте ему пароль **Set password** и переключите **Temporary** на 'Off' и сохраните.
6. Перейдите в раздел **Role mapping**, нажмите на **Assign role** и назначьте ему ранее созданную нами роль 'Admin' - **Assign**

### 4. Создайте роль SERVICE
1. Проделайте те же шаги, как и во втором шаге

### 5. Создайте клиента factory-client 
1. Перейдите в раздел **Clients** и нажмите **Create client**
2. **Client id** назначаете factory-client
3. После выставляете галочки у **Client authentication** и **Service accounts roles** (у остальных галочки убираете)
4. **Access settings** оставляете пустыми.
5. После создания перейдите в **Service accounts roles** и назначьте ему ранее созданную нами роль 'SERVICE'

### 6. Создайте клиента gateway-client 
1. Проделайте те же шаги, как и во втором шаге, но с некоторыми уточнениями:
2. **Client id** назначаете gateway-client
3. После выставляете галочки у **Client authentication** и **Standart flow ** (у остальных галочки убираете)
4. **Valid redirect URIs** 'http://localhost:8072/*' и Web origins '+'.
5. Роль 'SERVICE' назначать не надо.

### 7. При деплое (в моем случае self-hosted)
1. У 'gateway-client' в валидные редиректы также стоит указать айпишник (или, если назначили, доменное имя) сервера
2. Так же в основном и firm-realm перейти в **Realm settings** и выставить **Require SSL** на 'None' (в проде так делать явно не стоит)

## 🪟 Конфигурации сервисов
Конфигурации всех микросервисов централизованно управляются с помощью **Spring Cloud Config Server**. В текущей реализации конфигурационные файлы хранятся в закрытом Git-репозитории, что обеспечивает безопасность, аудит изменений и удобное версионирование.

Spring Cloud Config Server поддерживает несколько профилей (бэкендов) для хранения конфигураций. Выбор зависит от окружения (локальная разработка, тест или прод):

* **🐙 Git (основной способ):**
  Настройки хранятся в удаленном репозитории (GitLab, GitHub, Bitbucket). Это стандартный подход для Production-среды.
  * *Преимущества:* Полная история изменений, возможность отката (rollback), удобное разделение по веткам (например, `main` для продакшена, `dev` для тестирования).

* **📁 Native (локальная файловая система):**
  Конфиги загружаются из локальной папки на сервере или из папки `resources` (classpath) самого Config Server. 
  * *Применение:* Идеально подходит для локальной разработки и отладки, когда нет стабильного доступа к интернету или не хочется делать коммит в Git ради мелкой правки. Включается флагом `spring.profiles.active=native`.

* **🔐 HashiCorp Vault (для секретов):**
  Используется для безопасного хранения чувствительных данных (пароли от БД, API-ключи, токены). Spring Cloud Config может работать в связке с Vault, подтягивая обычные настройки из Git, а секреты — из защищенного хранилища. *(В вашем стеке Vault как раз развернут и настроен!)*

* **🗃️ JDBC (База данных):**
  Конфигурации хранятся в виде строк в реляционной базе данных. 
  * *Применение:* Удобно, когда настройки нужно менять динамически через UI-админку без необходимости делать Git-коммиты, но требует дополнительных накладных расходов на создание таблиц.

> **💡 Примечание по безопасности:** При работе с Git-репозиторием доступ Config Server к конфигурациям осуществляется по SSH-ключу или Personal Access Token, поэтому конфиденциальные данные остаются в безопасности.


## 🧪 Тестирование
Проект имеет комплексное покрытие тестами для обеспечения надежности, безопасности и стабильности работы всех компонентов микросервисной архитектуры. В проекте реализованы следующие уровни тестирования:

* **🧩 Юнит-тесты (Unit Tests):**
  Изолированное тестирование слоев бизнес-логики (сервисов), мапперов и утилит с использованием **JUnit 5** и **Mockito** без поднятия контекста приложения.

* **🔗 Интеграционные тесты (Integration Tests):**
  Проверка корректного взаимодействия приложения с внешней инфраструктурой (PostgreSQL, Redis, Liquibase). Выполняется с поднятием легковесных, одноразовых контейнеров баз данных с помощью **Testcontainers**, что гарантирует чистоту каждого тестового прогона.

* **🌐 Web-тесты (API/MVC Tests):**
  Тестирование REST-контроллеров, сериализации/десериализации JSON, обработки исключений и валидации входящих запросов (с использованием `@WebMvcTest` и `MockMvc`).

* **🛡️ Security-тесты:**
  Проверка механизмов ролевого доступа (RBAC) к защищенным эндпоинтам с помощью Spring Security Test.

* **📨 Kafka-тесты:**
  Тестирование асинхронного, событийно-ориентированного взаимодействия. Проверка логики продюсеров и консюмеров, сериализации сообщений и правильности работы с топиками (с использованием Testcontainers для брокера Kafka).

### 🏃‍♂️ Запуск тестов

Для локального запуска тестов используется встроенный Gradle Wrapper:

```bash
# Запуск тестов во всех микросервисах проекта
./gradlew test

# Запуск тестов для конкретного сервиса (например, factory-service)
./gradlew :services:backend:factory-service:test
```

> **💡 Примечание:** Для успешного прохождения интеграционных и Kafka-тестов убедитесь, что у вас запущен Docker (Docker Desktop или демон в фоне), так как он необходим для работы Testcontainers.
